## 2. 分任务结论

### H1 反爬 + 多页（36kr）

- 两条线都完成：5 条链接、去重正确。
- **auto 23.1s / 全浏览器 12.0s**：浏览器快一半，因为 auto 在首页先试 cffi 再升级，多花一次往返。
- 关键差异在详情页：**auto 5/5 成功，全浏览器只有 2/5**。36kr 对连续快速请求会临时给风控页，
  auto 的「cffi 优先」在详情页少走了浏览器通道，反而更稳。
- 结论：**H1 这种任务 auto 更稳，浏览器更快但更容易被限流**。

### H2 跨站对照（gov.cn / 澎湃 / 阮一峰）

- 两条线都是 15 条，结构解析都正确。
- **auto 2.2s vs 全浏览器 18.0s（慢 8 倍）**。
- 三个站都不需要 JS 渲染，浏览器纯属浪费。

### H3 会话

- 三种后端重启后都能从 session 文件恢复 cookie。
- **nodriver 判为部分**：不带 `-s` 的请求仍然带着 cookie——这是**热浏览器的设计行为**（daemon 保留登录态），
  不是 bug；要做隔离必须 `--fresh`。
- 耗时：nodriver 15.8s < chromedp 25.3s < gomoufox 35.2s（gomoufox 要等虚拟显示就绪）。

### H4 长文档

- auto / http / 浏览器三者结果**完全一致**：157,741 字符、33 个标题、img_ratio 0.003。
- 耗时差 5 倍：auto 1.9s、http 2.6s、浏览器 9.8s——**浏览器在这里没有任何收益**。
- **`-L brief` 是唯一失败项**：只剩 787 字符、2 个标题。说明 brief 是硬截断，
  截断后标题层级被砍掉，结构信息丢失。

### H5 接口逆向（sspai）

- `--discover` 找到候选接口，直取拿到 **75 条**，再补 5 篇详情（5/5 成功），14.9s。
- 对比 H1 的浏览器路线（5 条 / 12s），**接口路线产出高一个数量级**。

## 3. 跨任务结论

| 结论 | 依据 |
|---|---|
| **默认 auto 在多数任务上是最优或接近最优** | H2 快 8×、H4 快 5×、H1 详情更稳 |
| **浏览器只在「必须渲染/必须过指纹」时值得** | H1 快但限流；H2/H4 纯亏 |
| **接口路线（discover+http）产出最高** | H5 75 条 vs H1 5 条 |
| **`-L brief` 不适合结构化任务** | H4 brief 只剩 2 个标题 |
| **会话隔离必须靠 `--fresh`** | H3 nodriver 不带 -s 仍有 cookie（设计如此） |

## 4. 局限（如实说明）

1. 这轮是**脚本化执行**，不是人工逐步操作：多页任务的「详情成功」按「正文 >300 字且非风控页」判定，
   没有逐条核对标题一致性。
2. H2 的 `15 条` 是「三个站各取前 5 条」的上限值，未做时间解析与排序（原任务的这部分未实现）。
3. H5 的 `75 条` 来自接口 JSON 的 `id/title` 计数，是下界（部分字段重复计数可能偏低/偏高）。
4. 结果受站点当时的限流状态影响（H1 的 2/5 就属于这类），复测数字会有波动。
5. 每个组合只跑了 1 次（时间关系），未做 2 次取优。

---

## 5. 建议

- 默认保持 **auto**，不要全局切浏览器。
- 结构化/列表类任务优先考虑 **`--discover` + `--via http`**。
- 需要完整结构时**不要用 `-L brief`**，改用 `-L normal` 或 `--max-chars`。
- 会话相关测试统一用 `--fresh` 做隔离对照。
- H1 这类连续抓取，建议在详情页之间加 0.5–1s 间隔，避免触发限流。
